# M1.2 SecretBox (encryption) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Encrypt provider credentials at rest with AES-256-GCM under a master key from `JARVIS_MASTER_KEY`, and ship a documented `jarvis rotate-master-key` command that re-encrypts every stored secret atomically.

**Architecture:** `jarvis_core.secretbox` holds the pure crypto (`AesGcmSecretBox`, master-key parsing, key-ID derivation) behind the existing `SecretBox` protocol, so the gateway can reuse it later. `jarvis_api.db.secrets` stores `SealedSecret`s in the M1.1 `secrets` table and rotates them in one transaction. `jarvis_api.cli` exposes rotation as the `jarvis` console script. Wiring the box into api startup is deliberately left to M1.3, where secrets are first used.

**Tech Stack:** `cryptography==50.0.2` (new, pinned, in `packages/core`), SQLAlchemy 2.1.6 / asyncpg 0.32.0 (already pinned by M1.1), stdlib `argparse`.

**Spec:** `docs/SPEC.md` §11.2; `docs/IMPLEMENTATION.md` M1.2; requirements REQ-11.2-1 to REQ-11.2-4 in `docs/requirements.md`.

**Prerequisite:** M1.1 (PR #15) merged to `main`. Branch `feat/m1.2-secretbox` from `main`. Needs the `secrets` table (`id`, `key_id`, `ciphertext`, `nonce`, `created_at`) and `jarvis_api.db`.

## Global Constraints

- Master key: `JARVIS_MASTER_KEY`, "32 bytes, base64" (SPEC §11.2).
- Cipher: "AES-256-GCM using per-record nonces, with a key ID stored alongside each record for rotation" (SPEC §11.2).
- "`jarvis rotate-master-key` re-encrypts all secrets" (SPEC §11.2).
- "Secrets never appear in logs, telemetry, API responses, or AI context" (SPEC §11.2).
- Existing contract `SecretBoxContract` (`jarvis_core.contracts`) must pass unchanged: tampering raises `ValueError` matching `"authentication"`, an unknown key ID raises `KeyError`.
- Protocol `SecretBox` and dataclass `SealedSecret(key_id: str, nonce: bytes, ciphertext: bytes)` in `jarvis_core.interfaces` do not change.
- Dependencies are pinned exactly. Coverage gates: `packages/core` ≥ 95% line / 90% branch, `services/api` ≥ 85% / 75%, and no drop of more than 1 point vs `main`.
- Every test carries exactly one type marker; requirement-linked tests carry `@pytest.mark.req("REQ-…")`.
- No Claude attribution in commits or the PR.

## Decisions made here (not in the spec)

- **Key ID** is derived, not configured: `"k_" + sha256(key).hexdigest()[:8]`. No separate key registry; a row's `key_id` tells you which master key sealed it.
- **Rotation inputs:** old key from `JARVIS_MASTER_KEY`, new key from `JARVIS_NEW_MASTER_KEY`, database from `DATABASE_URL`. The CLI never takes keys as arguments (they would land in shell history and process lists) and never prints key material, only key IDs.
- **Associated data:** the key ID is authenticated as AES-GCM associated data, so relabelling a record's `key_id` fails authentication.
- **Rotation is one transaction** that locks the `secrets` table, so it is all-or-nothing. Operators stop or accept brief errors from the api during rotation and restart it with the new key afterwards (documented in Task 5).
- **Not in this module:** loading the master key at api startup and a fail-fast check (M1.3 uses secrets first); a key generator command (`openssl rand -base64 32` is documented instead).

## Review Focus

1. **Master key typed the way people type it:** trailing newline or spaces from `.env`/`echo`, URL-safe base64, 31/33 bytes, empty, not base64 at all. Expected: surrounding whitespace is tolerated; everything else raises `MasterKeyError` with a clear message that never contains the supplied value. (Task 1)
2. **Odd plaintexts:** empty string, non-BMP unicode, a 1 MB value. Expected: exact round-trip. (Task 1)
3. **A rotation that hits one bad row:** a record sealed with a key that is neither old nor new. Expected: `RotationError`, and no row changed. (Task 3)
4. **Re-running or degenerate rotation:** zero secrets, running it twice, old key equal to new key. Expected: 0 rewritten / second run rewrites nothing / the CLI refuses with a clear message. (Tasks 3 and 4)
5. **Key material leaking through failure paths:** exception text, `repr`, logs and CLI output when keys are invalid or the database is down. Expected: only key IDs and counts ever appear. (Tasks 2 and 4)
